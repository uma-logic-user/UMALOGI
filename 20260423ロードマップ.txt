  1. コードとインフラの脆弱性

  現状の問題点

  ① scheduler.py 常駐ループ（リスク: 最高）
  問題: Windows PC がスリープ / 再起動 / ブルースクリーンで即全停止
  現状: スケジューラが死んでも誰も気づかない（Discord通知なし）
  実績: 4/18・4/19 のデータ欠落はここが遠因

  ② SQLite 単一ファイル DB（リスク: 高）
  問題: data/umalogi.db の同時書き込みでロック衝突が発生しうる
  　　 → scheduler.py が 32bit/64bit 混在でサブプロセスを並走
  現状: WAL モードすら未設定（デフォルトは journal mode=delete）
  実績: reconcile/retrain/web-server が同時実行でエラーになるケース

  ③ netkeiba スクレイピング依存（リスク: 高）
  問題: HTML 構造が変わるたびに手動修正が必要（今回も3回発生）
  　　 CSS セレクタが 25列固定インデックスでハードコード
  現状: JVLink が失敗するとフォールバックが netkeiba 1本のみ

  ④ 認証情報の管理（リスク: 中）
  現状: .env が .gitignore で除外されているのは正しい
  問題: UMANITY_EMAIL / UMANITY_PASSWORD がログに平文で出る
  　　 scheduler.py の git auto-commit が .env を誤コミットするリスク

  モデル進化ロードマップ

  Phase 2.5（3ヶ月以内）— 優先: 高
  # 1. Calibration（確率の精度向上）
  from sklearn.calibration import CalibratedClassifierCV
  # 現状: 本命モデルの predict() は未校正確率
  # 修正: Platt Scaling または Isotonic Regression で校正
  # 効果: EV計算の精度が上がり、買い目の取捨精度が向上

  # 2. オッズ変動特徴量の活用強化
  # 既実装の odds_velocity を実際の予測に組み込む
  # → 大口投票が入ったレースは回避（マーケット効率性の利用）

  Phase 3.0（6ヶ月以内）— 優先: 中
  アンサンブル構成案:
    LightGBM（現在）    ← 構造的特徴（距離・血統・調教）
    + XGBoost         ← オッズ変動・市場効率
    + ニューラルネット   ← 非線形パターン（馬場・天候組み合わせ）

    → Stacking でメタモデルが最終予測を出す
    期待効果: AUC 0.692 → 0.71〜0.73（推定）

  長期的に最も有効な施策:
  競走馬の「疲労度指数」実装
    - 前走間隔 × 距離増減 × 斤量変化 × 輸送の有無
    - 現状特徴量に近走は入っているが、累積疲労の概念がない
    - これが実装できれば大穴馬の回避精度が大幅改善
